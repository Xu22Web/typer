# Typer 文件接收端脚本（线格式 v2）

把**任意文件**从一台机器"打"到另一台机器（终端、串口、KVM、远程桌面/云桌面里的接收端）：
逐片校验、断点续传、合并后校验整文件完整性。

接收端是**零依赖**的单文件 Node ESM：只用 Node 内置模块（`fs` / `crypto` / `zlib` …），**不需要 `npm install`**，
**Node ≥ 14** 即可运行。产物里不含 `node:` 前缀——它要 Node 14.18+，而很多目标机的 14.x 更早。

```bash
node typer-recv.mjs --help        # 查看全部选项
node typer-recv.mjs --selftest    # 校验编解码 / CRC / 帧解析
```

> 本目录里的 `.mjs` 与 `run.bat` 是**构建产物**（源码 `typer-recv.ts`，由 `pnpm build:tools` 用
> esbuild 打成压缩过的单文件，并生成双击入口 `run.bat`）。发到目标机时请保留 `.mjs` 扩展名：
> Node 靠扩展名识别 ESM，改名成 `.js` 后需要同目录有 `{"type":"module"}` 的 `package.json` 才能运行。

## 1. 怎么把脚本弄到目标机

| 方式                 | 做法                                                                                                                                                                                                                                                 |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **让 Typer 打进去**  | 文件页脚本卡点「插入接收脚本到文本输入」→ 内容区变成脚本全文并切到文本模式 → **在目标机打开记事本 / VS Code**，光标放进编辑区后开始输入，保存为 `typer-recv.mjs`。脚本是压缩过的单行文件，编辑器能正常承载；不要直接打进 cmd（控制台单行有长度上限） |
| **导出文件**         | 文件页/设置页的「导出脚本」把 `typer-recv.mjs`、`run.bat` 与本文档复制到指定目录（双击 `run.bat` 即可运行）                                                                                                                                          |
| **从安装目录直接取** | 安装后的 `<安装目录>\resources\tools\`（脚本、`run.bat` 与本文档都在，"打开脚本目录"按钮可直接定位）                                                                                                                                                 |
| **更新已有接收端**   | 目标机上已有能跑的接收端时，用文件页的「以文件方式发送脚本」（ASCII 6 位 + 压缩），几十秒即可把新版脚本传过去                                                                                                                                        |

用 Typer 发送脚本本身时建议选 **ASCII 6 位档**：脚本是纯 ASCII，6 位档不受代码页与输入法影响；
一份 50 KB 的脚本约 5 万字符，极速档（实测 ≈700 字符/秒）下一分半左右打完。

`run.bat` 是给人用的入口：双击即可运行接收端（等价于 `node typer-recv.mjs`；命令行参数原样转发、
退出码原样返回）。双击（不带参数）时窗口会在结束后停住等按键，方便看清结果——
窗口一闪就关往往让人以为什么都没发生，于是又双击一次，变成两个接收端同时跑（第二个会被单实例锁挡住）。
PATH 上没有 Node 时会给出提示并停住窗口。

## 2. 为什么不是"直接输入二进制"

| 问题     | 说明                                                                                     |
| -------- | ---------------------------------------------------------------------------------------- |
| 控制字符 | `\0` 无法输入；`\n` 是"回车提交"；`\t` 是 Tab 键；`\x1a`(Ctrl+Z) 在 Windows 控制台是 EOF |
| 终端行为 | 行缓冲有行宽上限、可能回显、启用 bracketed paste 会插入 `ESC[200~`                       |
| 链路质量 | 串口/远控/云桌面会丢字符或重复字符，且没有重传机制                                       |

所以数据先编码成**不含空白的符号流**，切成**每片一行**的帧；每片自带 CRC32，
接收端逐片校验、失败只重传该片，最后合并并校验整文件 SHA-256。

## 3. 字符档怎么选（决定要打多少字符）

耗时 ≈ `字符数 ÷ 每秒字符数`，所以"每字符承载多少比特"是第一杠杆。

| 字符档            | 每字符    | 每字节字符数 | 适用                                                                   |
| ----------------- | --------- | ------------ | ---------------------------------------------------------------------- |
| `b47`（终端推荐） | 5.447 bit | 1.47         | 用满美式布局上 47 个零 Shift 键：比 5 位档再少 8.2% 字符；**仅限终端** |
| `ascii32`（默认） | 5 bit     | 1.6          | 只用 `0-9` 与小写字母：**零 Shift**，远程桌面 / 云桌面首选             |
| `ascii64`         | 6 bit     | 1.33         | 字符数最少，但大写字母需要 Shift；每个修饰键切换多花约 25ms            |
| `hex`             | 4 bit     | 2            | 只在排查"到底是不是链路在改字符"时用                                   |

符号表定义在 `src/main/util/codec.ts`，收发两端共用同一份实现。前两档是位打包（每字符固定
`bits` 位），`b47` 是**分块基数转换**（每 32 字节当成一个大整数换成 base-47，所以 47 个符号
也能用满）：

- `b47`：`0-9 a-z` + `` ` - = [ ] \ ; ' , . / ``，共 47 个，全部无需 Shift。
  **只能打终端/命令行**：编辑器会把 `--`、`1/2`、`...` 自动更正成 `—`/`½`/`…`，还会自动闭合
  引号与括号，载荷当场就被改写。所以选"编辑器"模式时 UI 不提供这一档，主进程也会直接拒绝。
- `ascii32`：`0-9` + `a-v`，共 32 个；全部无需 Shift。
- `ascii64`：`0-9 A-Z a-z - _`；不含引号、括号与空白，编辑器不会自动闭合/缩进。
- `hex`：`0-9 A-F`。

四种符号表都不含 `@`，因此 `@T2` 在任何载荷里都不会出现——单行输入框里也能靠它切分帧。

## 4. 压缩

`none` 原样发送，`br` 整文件 Brotli 压缩后切片（分片是压缩流的切片，不是"每片各自压缩"）。
整文件压缩才能吃到跨片冗余，也才能到 5 位档的字符密度。

Typer 默认用 `auto`：先采样试压，几乎压不动（已压缩的图片/视频/ZIP）就直接发原字节，
省掉准备时间；可压缩数据用 Brotli 压缩。质量默认 `9`，**≤ 8 MB 的文件会自动升到 q11**
（多数文件准备多花 0.1~2 秒，换 3%~7% 更少的线上字节；再大就让准备阶段变成新瓶颈）。
想要固定质量就把 `quality` 设成 9 以外的值——`9` 与默认值同值，一律按"自动"处理。

> **只传原字节**：不作容器重打包/解包，接收端合并后校验的 SHA-256 必须等于源文件。

## 5. 线格式 v2（收发双方唯一契约）

每帧**一行**：ASCII 帧头 + 不含空白的符号载荷。

```
开始帧  @T2H <job> <total> <size> <wire> <chunk> <nameB64> <alphabet> <compression> <mode> <hcrc> <sha256>
数据帧  @T2D <job> <seq> <bytes> <crc32> <hcrc> <payload>
结束帧  @T2E <job> <total> <size> <wire> <hcrc> <sha256>
续传令  @T2R <job> <total> <missing>
```

| 字段          | 含义                                                                         |
| ------------- | ---------------------------------------------------------------------------- |
| `job`         | 任务标识（8 位小写 hex）。接收端用它隔离工作目录                             |
| `total`       | 数据片总数（不含开始/结束帧）                                                |
| `size`        | **原始文件**字节数（整文件哈希按它复核）                                     |
| `wire`        | **线上**字节数（压缩后的字节数；`none` 时等于 `size`）                       |
| `chunk`       | 每片线上字节数                                                               |
| `seq`         | 0 基片号                                                                     |
| `bytes`       | 本片线上字节数（末片可小）                                                   |
| `crc32`       | 本片线上字节的 CRC32（8 位小写 hex）                                         |
| `hcrc`        | **帧头** CRC32：本行 `hcrc` 之前所有字段以空格连接后的 CRC32（8 位小写 hex） |
| `alphabet`    | `ascii32` / `ascii64` / `b47` / `hex`                                        |
| `compression` | `none` / `br`                                                                |
| `mode`        | `term`（CR 提交）/ `editor`（真回车）/ `line`（无换行，靠 `@T2` 分帧）       |
| `payload`     | 符号流                                                                       |
| `nameB64`     | 文件名的 UTF-8 base64url（`-` 表示不指定）                                   |
| `sha256`      | 整文件 SHA-256                                                               |
| `missing`     | 缺失片号，逗号分隔，支持 `a-b` 区间（`-` 表示无缺失）                        |

**回执**（接收端输出，`#` 前缀）：`#FAIL <seq> <code>` / `#MISS <ranges>` / `#DONE <size> <sha256> <path>` /
`#BAD <kind>` / `#PROBE …` / `#STATS …`。

> **为什么帧头也带 CRC**：链路上偶发丢一个字符时，`size: 2688 → 268` 这类改动并不改变字段数量，
> 接收端会按错误规模合并——这是最难排查的一类故障。带 `hcrc` 后，任何帧头改写都会在解析阶段被拒绝，
> 接收端只报 `#FAIL`，绝不会产出看似正常的坏文件。

**退出码**：`0` 成功且校验通过；`2` 数据不全；`3` 完整性校验失败；`4` 参数或 IO 错误。

线格式与符号表的**唯一实现**在 `src/main/util/frame.ts` 与 `src/main/util/codec.ts`：
Typer 主进程与接收端脚本引用同一份代码，收发两端不会出现实现漂移。

## 6. 选项

```
node typer-recv.mjs [选项]
  -o, --out <path>        输出文件（默认 <分片目录>/<开始帧里的文件名>）
  -d, --dir <path>        分片工作目录（默认 ./.typer-<job>）
      --in <file>         从文件读取帧（默认读标准输入）
      --cooked            强制行缓冲读入（TTY 下默认 raw：不回显、无行宽限制）
      --no-resume         忽略已有分片全部重收（默认：校验通过即跳过）
      --no-overwrite      输出文件已存在时拒绝覆盖
      --report <path>     续传报告 JSON（默认 <dir>/resume.json；写 "-" 关闭）
      --keep-parts        合并成功后保留分片
      --probe             只统计收到了什么，不落盘（确认链路能过非 ASCII 字符）
      --stats             结束时打印字符数/字节数与耗时
      --progress <mode>   进度回显：auto（终端下自动，默认）/ on / plain（逐行，写日志用）/ off
      --ime <mode>        启动时切英文直输、退出时还原：auto（默认，交互式终端才切）/ on / off
  -q, --quiet             只保留 #FAIL / #MISS / #DONE / #BAD
  -v, --verbose           打印逐片处理信息（很吵，仅排障用）
      --selftest          自检编解码、CRC、帧解析
  -h, --help              显示帮助
```

### 进度回显

大文件传输要几十分钟，光等一个 `#DONE` 无法判断"在慢慢收"还是"已经卡住"。接收端按阶段回显，
并且**按终端宽度自动选排版**（宽屏两行、窄屏一行、写日志一行逐行输出）：

| 阶段   | 一句提示                                                                                    |
| ------ | ------------------------------------------------------------------------------------------- |
| 启动   | `输入法  布局 0804 / 输入法开启 → 布局 0409 / 输入法关闭`                                   |
| 等待   | `⠹ 等待开始帧 · 已等 00:12` + 一句"在 Typer 里点发送"                                       |
| 开始帧 | `✔ 接收开始  108 片 · 文件 19.8 MB（线上 7.6 MB，每片 16 KB）· ascii32 / none / term`       |
| 收片   | 两行（见下）                                                                                |
| 断流   | `! 已 12 秒没有任何输入（41/108 片）：上游可能停了、链路卡住…`                              |
| 合并   | `⠹ 合并校验  108/108 片 · 已用 04:08` / `████░░…  62.0%  12 MB/19.8 MB  解压并校验 SHA-256` |
| 完成   | `✔ 传输完成  19.8 MB · 108 片 · 用时 4 分 12 秒 · 平均 80.3 KB/s · SHA-256 已校验`          |

宽终端（≥92 列，两行原地重绘）：

```
⠹ 接收中  41/108 片 · 当前片 63% · 已用 03:21
████████████████████████  38.4%  7.6 MB/19.8 MB  82.4 KB/s  剩余 02:29
```

中等宽度（两行、字段更省）：

```
⠹ 接收中  41/108 片 · 当前片 63%
███████████████░░░░░  38.4%  7.6 MB/19.8 MB  82 KB/s  剩余 02:29
```

窄终端 / 不支持 ANSI（单行原地重绘，断流时转圈变 `!`）：

```
⠹ ██████░░ 38% 41/108 片 当前片 63% 82 KB/s 剩余 02:29
```

重定向到日志（`--progress plain` 或本身就是管道）：每 5 秒一行，无颜色、无 `\r`、无转圈：

```
接收中  [########----------------]  38.4%  41/108 片  当前片 63%  7.6 MB/19.8 MB  82 KB/s  剩余 02:29  已用 03:21
```

几条设计上的硬约束：

- **行永远不会超出终端宽度**：排版层按「中文/全角算两格」计算可见宽度并裁剪。
  旧版按**字符数**补空格，行一超宽终端就自动折行，而折行会让"光标上移重画"错位——
  于是同一次传输里"有时原地刷新、有时一行行往上滚"同时出现；
- **能不能原地重绘按能力降级**：启动时探测控制台能否开 ANSI（VT）→ 两行块；否则只依赖 `\r` 的单行；
  再不行就逐行写日志。`--progress plain` 可强制最后一种；
- **整体进度包含片内进展**（`已收片数 + 当前片比例`），所以进度条是连续走的，不是一格一跳；
  但已经开始收的片不会重复累加，重放同一片也不会超过 100%；
- **速率**取最近 8 秒窗口（不是从开始到现在的平均值），卡顿恢复后 ETA 会跟着回来；
- **断流判据是「最后一次收到字节」**，不是「最后一次收下整片」——一个 16 KB 的片要打几十秒，
  用"片"当判据会在这期间反复误报；真的 10 秒没有任何输入才提示，且 20 秒内不重复；
- 颜色与方块字符只在"终端 + 代码页 65001 + 支持 ANSI"时启用（`NO_COLOR` 可关），
  所以重定向到文件或贴进工单里的日志永远是纯文本；
- 终端窗口被 resize 时按新宽度重排一次，不会留下残影。

### 输入法与终端准备

帧是**逐字符打进这个控制台窗口**的：中文输入法开着时，字母键会被吃成候选上屏，帧内容要么丢、要么变形。
所以脚本启动时做一次和主程序 `typing-host.ps1` 完全相同的处理：把目标窗口切到英文（美国）布局、
关掉输入法、切英数模式；**结束时（完成 / 中止 / Ctrl+C）再还原**，不把用户的输入法留在英文上。

实现上只调用一次**隐藏的** PowerShell（内联 C#，无临时文件、不受执行策略限制），一次做三件事：

1. `SetConsoleOutputCP(65001)`：中文提示与方块字符正常显示（替代旧版那次 `chcp` 子进程）；
2. 打开 `ENABLE_VIRTUAL_TERMINAL_PROCESSING`：两行原地重绘的前提；失败就降级成单行；
3. 切英文直输，并记下切换前的布局句柄 / 输入法开关，供退出时还原。

开关与边界：

- `--ime auto`（默认）：只在"真的在用键盘"（stdin 是终端且没给 `--in`）时才切，离线校验不碰系统状态；
- `--ime off`：完全不碰输入法（控制台初始化仍然做，否则中文/方块字符显示会不对）；
- PowerShell 不可用 / 被策略禁止：跳过并打一行 ASCII 提示（`[!] console init unavailable …`），
  收片流程不受影响，这时请用 `--progress plain`（输出没有颜色与方块字符）；
- 已经切过就不再重复切；什么都没改过就不会去"还原"，避免把用户后来手动改的状态又改回去。

### 单实例保护

同一个分片目录只允许一个接收端写：启动时用 `wx` 原子创建 `.recv-lock`（内容是 PID）。
目录已被另一个**还活着**的进程占用时，本次直接停下并说明（退出码 4），
避免两份进程互相覆盖分片、各自合并一次（也就是"多开了一份"）。
持有者已经消失的陈旧锁会自动接管；确认无误但仍在报占用时，删掉 `.recv-lock` 再试。

### 传输期间不打印逐片日志

终端回显要经过远控/云桌面回传给操作者，屏幕更新往往比按键转发慢一个数量级。
所以接收端在 raw 模式下**关掉回显**，并且只回显进度本身（可用 `--progress off` 关掉），
不逐片刷屏；`--verbose` 仅用于排障。

### 断点续传

- 每片落到 `p<seq>-<crc32>.bin`，文件名本身带校验值：重启后同名同 CRC 的片直接跳过。
- 中断后重跑，接收端会自动读取 `meta.json` 与已有分片；缺片时打印 `@T2R` 令牌。
- 在 Typer 里粘贴令牌，即只补缺失片；补完自动发结束帧，接收端合并并校验。

## 7. 目标环境

| 环境                                      | 建议                                                                                                       |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Windows 终端 / conhost / Windows Terminal | 默认设置即可：raw 模式，5 位档最快                                                                         |
| 云桌面 / 远程桌面                         | 直接可用：只发真实按键；优先用 5 位档（零 Shift），详见 `docs/remote-desktop-optimization.md`              |
| 记事本 / VS Code                          | 用「编辑器」模式（真回车）+ ASCII 6 位档；接收端脚本首次也可以用这种方式打进去（单行长脚本对编辑器无压力） |
| 单行输入框                                | 用「单行框」模式（帧间无换行）；只能配 ASCII / Hex 档                                                      |
