# 文件传输提速：模型、实测与取舍

这份文档解释 Typer 文件传输"为什么这么快 / 为什么有时快不了"，以及每一层还能怎么调。
结论都来自本机实测（Windows 11，Node 24）；样本与数据见第 5 节的对照表。

## 1. 唯一的耗时公式

```
字符数 ≈ ceil(线上字节 × 8 / 每字符比特数) + 帧头开销
总耗时 ≈ 字符数 ÷ 每秒字符数 + 准备时间
```

三项各自对应一个可调的层：

| 层         | 手段                                               | 典型量级                              |
| ---------- | -------------------------------------------------- | ------------------------------------- |
| 每字符比特 | 4 bit（hex）→ 5 bit（ASCII）→ 5.447 bit（47 进制） | 9.64 M → 7.70 M → 7.07 M 字符         |
| 线上字节   | 整文件 Brotli；不可压缩数据直接跳过                | 4.81 MB → 4.53 MB（该文件几乎压不动） |
| 每秒字符   | 稳健 / 快速 / 极速三档、关回显、逐动作投递         | 446 / 446 / 实测 ≈700（压力阀自适应） |

## 2. 字符密度与 Shift 的取舍

帧是**逐字符**打出去的，一个字符就是一次注入，所以"每字符能带多少信息"直接等于带宽：

- 十六进制 4 bit：一个字节 2 个字符。
- ASCII 6 bit：一个字节 1.33 个字符，但一半字符是大写，需要 Shift。
- ASCII 5 bit：一个字节 1.6 个字符，全部是数字/小写字母，**完全不发 Shift**。
- 47 进制（5.447 bit）：一个字节 1.47 个字符，同样零 Shift。美式布局上共有 47 个无需 Shift 的
  可打印键，但位打包要求符号表大小是 2 的幂，所以这一档改用**分块基数转换**：每 32 字节当成一个
  大整数换成 47 进制（32 字节 → 47 个字符）。实测比 5 位档再少 8.2% 字符，与
  `log2(47) / 5` 的理论值一致。**只能打终端**：编辑器会把 `--`、`1/2`、`...` 自动更正，还会
  自动闭合引号与括号，载荷当场被改写；因此编辑器模式下不提供这一档，设置层也会就地纠正这种组合。

早期版本用过 15 bit 的 CJK 符号表（一个字节 ≈ 0.53 个字符），但它依赖 `KEYEVENTF_UNICODE`
报文；实测远程桌面客户端会忽略该报文（把 `wScan` 低 8 位当扫描码转发），该路径已整体移除。

在当前实现里，凡是需要 Shift 的字符都要多付一次修饰键切换：宿主必须把修饰键单独 `SendInput`
并等 15ms（抬起前再等 10ms），否则 RDP 会把同批修饰键合批丢掉。这两个间隔可在
**设置 → 通用 → 修饰键时序** 里调整（默认 15 / 10，链路慢时调大到 30~60ms 更稳），
帧路径与文本路径使用同一份设置。

这个代价比"少几个字符"大得多：载荷里大写与符号是**交替出现**的，需 Shift 的字符占比为 p
时，切换次数接近 `字符数 × 2p(1−p)`（实测与公式吻合）。`ascii64` 与 `hex` 分别有 42% /
38% 的字符需要 Shift，于是每打一个字符平均要多付 ≈45% × 25ms ≈ 11ms 的修饰键开销；
而一个字符本身的注入间隔在 446 字符/秒下只有 2.2ms。实测 `ascii64` 的字符数虽然比
`ascii32` 少 16%，总耗时却是它的 **3~5 倍**（见第 5 节的实测表）。所以默认选零 Shift 的
5 bit 档，终端下用 47 进制档。

> 为什么不继续提高密度：再往上一档只能用 Shift 才能打出的字符（或非美式布局的键位），
> 而一次修饰键切换就要 25ms——已经亏回去了；而任何高密度符号表都要有对应的物理键位或
> Unicode 报文，后者在 RDP 下不可用。

## 3. 压缩：整文件，而不是逐片

旧实现（逐片 deflate）对已压缩的 ZIP 几乎没收益（99.3%），对文本也只有约 1/3 的字符节省。
现在改成**整文件压缩后再切片**：

- 能吃跨片冗余：文本/代码/JSON 的重复模式跨片存在，逐片压缩吃不到；
- 分片是压缩流的切片，`wire` 与 `total` 在发送前就精确已知，耗时预估不再是估算。

实测（同一份 19.4 MB 未压缩条目流 × Brotli）：

| 质量 | 比例  | 耗时   |
| ---- | ----- | ------ |
| q5   | 17.4% | 1.1 s  |
| q7   | 15.5% | 1.5 s  |
| q9   | 14.9% | 6.5 s  |
| q11  | 13.5% | 99.7 s |

`q9` 一直是默认档：再往上提升有限。不过“提升有限”要分规模看——本机用真实文件实测
（16 KiB 片、文本/代码/JSON），小文件的 q11 代价与 q9 同量级，而收益是确定的：

| 文件              | 大小   | q9 → q11 线上字节 | 字符数（5 位）q9 → q11 | q11 耗时 |
| ----------------- | ------ | ----------------- | ---------------------- | -------- |
| `tools/README.md` | 18 KB  | 7,344 → 6,856     | 11,751 → 10,970        | 55 ms    |
| `frame.ts`        | 31 KB  | 9,268 → 8,792     | 14,829 → 14,068        | 93 ms    |
| `FilePanel.vue`   | 35 KB  | 10,536 → 9,906    | 16,858 → 15,850        | 86 ms    |
| `pnpm-lock.yaml`  | 253 KB | 75,874 → 73,335   | 121,399 → 117,336      | 642 ms   |
| 8 MB 合成文本     | 8 MB   | —                 | —                      | 2.1 s    |

所以现在的规则是：`quality` 等于默认值 `9` 时视为“自动”，**8 MB 以内升到 q11**（准备最多多花
~2 秒，而 8 MB 文件键入要几十分钟）；更大的文件维持 q9，避免准备阶段变成新瓶颈。
想要固定质量就把等级设成 9 以外的值。

已压缩的容器（VSIX / ZIP / DOCX 这类 deflate 过的包）Brotli 只能再省 2%~3%——所以
**采样试压后直接发原字节**，省掉几十秒准备时间。

## 4. 每秒字符数：真正的瓶颈

`SendInput` → 目标程序 → （云桌面时）客户端把按键转发到远端 → 远端回显回来。
任何一段慢，都会体现在"每秒字符数"上。

可做的事：

1. **关回显**：接收端 raw 模式 + 传输期间不打印。云桌面的屏幕回传往往比按键转发慢一个数量级。
2. **逐动作投递 + 压力阀**：每个字符一次 `SendInput`（数据帧丢不起字符），宿主记录每次投递
   被目标端输入队列拖住的时长，并从后续间隔里扣掉，让节奏贴着目标端的真实消化能力跑。
   > 实测教训：一次 `SendInput` 带几百个动作（攒批直投）听起来更快，但在真实 cmd 接收端上
   > **会静默丢字符**——一次 16 KiB 的片丢过 7 个和 587 个字符。逐动作投递同样条件下零丢失，
   > 所以三档节奏都改回逐动作，速度差异只来自"要不要等那 1ms"。
3. **零延迟**：极速档不再逐字符等 1ms。丢字符不会写坏数据——该片 CRC32 会失败并被单独重传；
   开始帧/结束帧还会连发 3 遍（丢一个字符就整趟重来的那两帧，重复最划算）。
4. **减少帧头**：16 KiB 片下，帧头（约 30 字符）占比 <0.4%。

实测参考（本机，真实 cmd 接收端，逐动作投递）：

| 档位 | 帧内间隔 | 实测                                 |
| ---- | -------- | ------------------------------------ |
| 稳健 | 1 ms     | ≈446 字符/秒，2.7 万字符零丢失       |
| 快速 | 1 ms     | 同上（省的是片间停顿）               |
| 极速 | 0        | ≈700 字符/秒（由目标端消化能力封顶） |

> 极速档的真实速度必须在**目标链路**上测：Typer 是本机注入，但字符最终要穿过云桌面客户端。
> 用接收端 `--stats` 看 `cps`，或看 Typer 的运行进度与总耗时。

## 5. 实测：五类样本 × 四种编码

16 KiB 片、Brotli q11 的纯键入耗时（446 字符/秒，**含修饰键切换**；每格上一行是总耗时，
下一行是字符数）：

| 样本                      | 大小   | `b47`          | `ascii32`  | `ascii64`   | `hex`       |
| ------------------------- | ------ | -------------- | ---------- | ----------- | ----------- |
| 文档 `tools/README.md`    | 19 KB  | **25 秒**      | 27 秒      | 2 分 19 秒  | 3 分 23 秒  |
|                           |        | 10,984         | 11,946     | 10,001      | 14,859      |
| 代码 `FilePanel.vue`      | 36 KB  | **33 秒**      | 36 秒      | 3 分 12 秒  | 4 分 37 秒  |
|                           |        | 14,843         | 16,149     | 13,505      | 20,111      |
| 大文本 `pnpm-lock.yaml`   | 253 KB | **4 分 03 秒** | 4 分 24 秒 | 23 分 30 秒 | 34 分 18 秒 |
|                           |        | 108,159        | 117,791    | 98,235      | 147,118     |
| 单行脚本 `typer-recv.mjs` | 52 KB  | **57 秒**      | 1 分 02 秒 | 5 分 30 秒  | 7 分 54 秒  |
|                           |        | 25,314         | 27,553     | 23,015      | 34,354      |
| 已压缩位图 `icon.png`     | 50 KB  | **2 分 39 秒** | 2 分 53 秒 | 15 分 29 秒 | 22 分 26 秒 |
|                           |        | 70,910         | 77,220     | 64,411      | 96,429      |

`b47` 在每个样本上都最快（字符数稳定为 `ascii32` 的 91.8%）；`ascii64` 字符数最少（83.5%）
却慢 3~5 倍——**只看字符数会把人骗了**。复现：`node scripts/bench-transfer.mjs <文件>`
（`--alphabet` 只看单档，`--no-shift` 关掉切换统计，`--emit out.txt --verify` 把帧交给
真接收端逐字节校验）。

## 6. 不可压缩的大文件

| 文件类型                | 典型比例 | 100 MB 的字符数（5 位）      | 446 字符/秒                   |
| ----------------------- | -------- | ---------------------------- | ----------------------------- |
| 文本 / JSON / 源码      | 10–25%   | 1,700 万 – 4,200 万          | 10–26 小时                    |
| 未签名 ZIP / JAR / DOCX | 10–20%   | 1,700 万 – 3,400 万          | 10–21 小时                    |
| JPEG / PNG / MP4 / 7z   | 100%     | 1.68 亿（47 进制档 1.54 亿） | 104 小时（47 进制档 96 小时） |

对最后一类，键入方式不可能在小时级完成。界面会直接标注不可行，并建议拆分发送或改用其它通道。

## 7. 可靠性：速度再快也不能写坏数据

- 每片 `CRC32`：坏片只影响自己，重传成本 = 一个片（16 KiB）。
- 每帧帧头 `hcrc`：帧头字段（`size`/`bytes`/`seq`…）被丢字符改写时，字段数量往往不变，
  接收端会按错误规模合并。帧头自带 CRC32 后，这类"静默错位"在解析阶段即被拒绝。
- 整文件 `SHA-256`：合并后复核，任何一位不同都会明确报 `#BAD sha256` 而不是静默产出坏文件。
- 只传原字节：不做容器重打包，签名与哈希都不受影响。
- 发送前自检：每帧渲染后立即解回并逐字节比对；编码器出错会在发送前就停下。
- 默认 `--keep-parts` 关闭：成功后清掉分片；失败时保留，可继续续传。

## 8. 复现与测速

```bash
# 开发机上离线跑完整链路（不产生按键）：字符数、各档耗时、接收端逐字节校验
node scripts/bench-transfer.mjs "D:\path\to\file" --emit out/bench/frames.txt --verify

# 目标机上测真实吞吐
node typer-recv.mjs --stats

# 目标机上先确认链路能不能原样送过一帧
node typer-recv.mjs --probe
```
