# 远程桌面（RDP / 云桌面）场景适配与提速

本文回答两个问题：**在只转发键盘事件的远程桌面里，Typer 哪些能力可用**，以及**从注入事件层面还能怎么提速**。
文中区分「已验证」「按协议与实测推断」「需在目标链路上实测」三类结论，未实测的地方都标了 `待实测`。

## 1. 两条注入路径与当前取舍

| 路径         | 底层事件                                        | 本机 / 普通窗口 | RDP / Citrix / 部分 KVM         |
| ------------ | ----------------------------------------------- | --------------- | ------------------------------- |
| 真实按键     | `SendInput` + 虚拟键码（需要 Shift 时带修饰键） | ✅              | ✅ 客户端把它翻译成扫描码后转发 |
| Unicode 报文 | `KEYEVENTF_UNICODE`（`VK_PACKET`）              | ✅              | ❌ 客户端不按报文处理           |

实测证明：RDP 客户端会**忽略 `KEYEVENTF_UNICODE`**，把 `wScan` 的低 8 位当扫描码转发。
用全角标点 `，。！？；：（）【】《》` 测试，远端得到 `-1S][78QW90`——逐字符合「码点 & 0xFF →
扫描码 → 远端布局」的映射。因此 Typer **已经彻底移除 Unicode 报文路径**，只保留真实按键。

由此得到三条结论：

1. **文本模式只支持有物理键位的字符**：中文 / emoji 等会在开始前列出并报错，不会静默丢字。
2. **文件传输不需要额外开关**：帧正文与行尾都用真实按键（真回车）。
3. **字符档默认用零 Shift 的 5 位档（`ascii32`）**：大写与符号需要 Shift，而修饰键在这类链路里要单独一次调用并留间隔（见第 2 节），所以默认避开 Shift。

## 2. 修饰键必须与主键分开下发

实测（同一台云桌面，`Shift+1` 期望得到 `!`）：

| 做法                                  | 结果                        |
| ------------------------------------- | --------------------------- |
| 修饰键与主键在同一次 `SendInput`      | ❌ 得到 `1`（Shift 丢失）   |
| 拆成独立调用、中间**无延时**          | ❌ 仍丢失                   |
| 拆成独立调用、中间 **10ms**           | ✅ 得到 `!`                 |
| 拆成独立调用、中间 30 / 60 / 120ms    | ✅                          |
| 一次调用 + 递增的 `KEYBDINPUT.time`   | ❌ 无效（客户端不看时间戳） |
| 按住 Shift 连打多个键（键间 10~30ms） | ✅ `!@#$` 全对              |

当前实现：宿主维护「当前按住的修饰键掩码」，只在状态切换时付间隔（默认按下后 15ms、
抬起前 10ms，可通过 `type` 请求的 `modLeadMs` / `modTailMs` 覆盖），连续需要同一修饰键的字符保持按住。

「修饰键过渡 + 主键 down/up」在宿主里是一个**不可打断的动作组**：停止 / 暂停的取消点只落在
动作组之间，一旦开始按修饰键，这一组字符必定打完——不会留下「Shift 按着、字符却没打出来」的
中间态。暂停生效时还会先把修饰键全部抬起，避免长时间按住影响用户后续手动操作；继续时会重新走
一次开始倒计时再接着打。

## 3. 必做配置

| 位置             | 设置                                      | 原因                                                 |
| ---------------- | ----------------------------------------- | ---------------------------------------------------- |
| Typer → 文件传输 | 字符档 = **ASCII 5 位**（默认，零 Shift） | 每个 Shift 切换都要付约 25ms 间隔                    |
| Typer → 文件传输 | 传输节奏 = 先实测再定                     | 见第 5 节                                            |
| **本机**输入法   | 切到**英文**                              | 注入的按键先经过前台窗口（mstsc）所在线程的输入法    |
| **远端**输入法   | 切到**英文**                              | 远端同样会拦截真实按键；Shift 还可能被当成中英文切换 |
| 本机             | 关闭「粘滞键」                            | 粘滞键会让修饰键保持按下，干扰后续输入               |

> `SendInput` 注入的事件进入**本机前台窗口**的输入队列，先被本机输入法处理，再由 RDP 客户端转发。
> 所以「输入变拼音」这类现象发生在本机，而不是远端。

## 4. 事件级可优化项

RDP 的吞吐上限 ≈ 每秒能穿过客户端的键盘事件数。所有提速手段最终都落在两件事上：**减少事件数**、**减少每次事件的固定开销**。

### 4.1 已经在做的

- **单次调用批量提交**：一次 `SendInput` 最多 256 个事件（约 128 个字符），客户端可以把它们合并进较少的快路径 PDU，而不是每字符一次往返。
- **修饰键分离 + 按住区间**：修饰键单独调用并留 15/10ms，连续同修饰键的字符只付一次切换。
- **压力阀自适应**：宿主记录每次投递被输入队列拖住的时长，从后续间隔里扣掉并补等，让节奏贴着目标端的真实消化能力跑（日志里的 `blockedMs` / `valveMs` 就是它）。
- **零延迟档**：极速档不再逐字符等 1ms，速度完全交给目标端。
- **零 Shift 字符档**：`ascii32`（数字 + 小写字母）完全不触发修饰键切换。
- **关回显**：接收端传输期间不打印，避免屏幕回传抢带宽。
- **整文件压缩**：直接减少要打的字符数，是唯一「不花事件预算」的提速。

### 4.2 可以加、但当前未做的

| 手段                                   | 收益                                                                         | 代价 / 风险                                                       |
| -------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **扫描码直投**（`KEYEVENTF_SCANCODE`） | 字符由**远端**布局决定，本机布局与本机输入法的影响进一步降低（实测可直接用） | 现有布局表按虚拟键写，需要补一张「字符 → 扫描码」表并重验全部布局 |
| **修饰键间隔自适应**                   | 按实测延迟动态调 10~30ms，兼顾兼容与速度                                     | 需要能观测「修饰键是否生效」（只能靠抓字/CRC 回传间接判断）       |
| **事件数再压缩**                       | 同一批里重复的前导/结尾按键可以合入同一 PDU                                  | 取决于客户端实现，收益不稳定                                      |

### 4.3 明确不可行 / 不划算的

- **省掉 keyup**：真实按键必须成对。只发 keydown 会让远端认为键一直按着，下次同键会被当成自动重复，修饰键状态也会错乱。（Unicode 报文路径的 `noKeyUp` 只对报文生效，真实按键不受它影响。）
- **把整帧塞进一次 `SendInput`**：本地实测会在控制台类目标里静默丢字符（一次 16 KiB 片丢过 7～587 个字符）。RDP 下同样有远端输入队列，丢字符只能整片重传，反而更慢。
- **按住字母键让远端自动重复**：自动重复速率由远端键盘设置决定，且无法精确控制字符数，数据场景不可用。
- **剪贴板 / 文件拖放**：多数受限环境已禁用；与「只能键盘」的约束冲突。

## 5. 怎么在目标链路上实测

1. 远端跑接收端并打开统计：`node typer-recv.mjs -o out.bin --stats`。
2. 三档节奏各发一片（16 KiB），记录 `cps` 与最终耗时。
3. 对照 Typer 日志里的 `blockedMs` / `valveMs`：
   - 两者长期为 0 → 目标是「链路/客户端」封顶，本机还有余量，可以再加大批；
   - 明显大于 0 → 目标端消化不过来，调大批次只会增加丢字符与重传，应停在当前档位。
4. 少量脚本即可估算上限：`node scripts/bench-transfer.mjs <文件> --emit frames.txt --verify`。

> 探针脚本已随 Unicode 路径一起移除；需要重新评估一条新链路时，可参照本节思路写一个临时的
> PowerShell + 内联 C# 小脚本（把 `Shift+1` 拆开成独立 `SendInput` 并调整间隔），验证后再接入。

## 6. 客户端 / 环境侧建议（不改代码）

- 优先用 **mstsc（Windows App）**，其对注入按键的转发最完整；部分第三方客户端会过滤标记为注入的键盘事件（`待实测`，与客户端实现有关）。
- 关闭与输入无关的重定向（驱动器、剪贴板、打印机）可减少通道竞争；如果屏幕回传明显拖慢输入，降低远端分辨率或关闭动画/透明效果。
- 远端不要开「粘滞键 / 筛选键」：它们是远程端对 Shift 组合最常见的干扰源。
- 远端终端里跑接收端时保持窗口**在前台且获得焦点**；Typer 的焦点守护会把焦点变化当成异常提示（`strict` 模式下直接中止）。

## 7. 仍然解决不了的部分

| 场景                       | 说明                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| RDP 下输入中文 / emoji     | 没有物理键位；Typer 会在开始前列出这些字符并拒绝开始                 |
| 远端输入法停在中文态       | 真实按键会被拼成拼音、真回车会被候选窗吃掉；必须在远端切英文         |
| 以管理员权限运行的远端程序 | UIPI 限制，需要本机与目标权限一致（本机侧还会遇到 Windows 会话隔离） |
| 锁屏 / UAC / 安全桌面      | 无法注入                                                             |
